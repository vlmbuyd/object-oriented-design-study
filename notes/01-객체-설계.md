# 01. 객체, 설계

> 💡 (비어 있음 — 한 문장 요약 미작성)

## 내가 먼저 도달한 것

- 객체지향 설계에서는 객체들 간에 협력이 기본이기 때문에 '의존성'은 필연적이다. 하지만 이 의존성으로 인해 결합도가 높아지지 않도록 관리하는 것이 중요하다. 그러기 위해서는 의존한 객체의 세부 구현을 덜 아는 것이 중요하다. 상태와 로직이 캡슐화되어 내부에서 자율적으로 기능할 수 있도록 하는 것이다.
- 자율적인 객체는 내부 구현을 외부에 노출하지 않고, 자신의 문제를 스스로 책임지고 해결한다.
- 외부에서 의존하는 객체의 내부 구현을 덜 알수록 그 객체는 자율적이고 결합도는 낮아진다.
- **자율성을 높였지만 결합도가 상승한 사이드 이펙트가 따라왔다. 자율성과 결합도가 항상 반비례 관계인지는 잘 모르겠다.**
  → 힌트를 받기 전에 스스로 감지한 지점. 이 장에서 가장 중요한 균열을 먼저 짚었다.

## 책이 더 밀어준 것

- 자율성은 **객체 하나만 놓고 판정하는 속성**이다 — 자기 데이터를 스스로 처리하는가 (p.24~26). 첫 정리는 이걸 "객체 간 의존성의 척도 = 얼마나 변경하기 쉬운가"로 두었는데, 그러면 객체 하나로는 판정할 수 없게 된다.
- 자율성↑ 이 결합도↓ 를 보장하지 않는다. TicketOffice가 스스로 티켓을 팔게 하려면 Audience를 알아야 하므로 **없던 의존성이 새로 생긴다**. 설계는 트레이드오프의 산물 (p.33).
- 그래서 결합도를 두 층으로 나눠 보게 됨.
  - **누구를 아는가**(존재) — 협력하는 이상 피할 수 없고, 자율성을 높이면 오히려 늘어난다
  - **그 안이 어떻게 돌아가는지 아는가**(구현) — 캡슐화가 줄이는 건 이쪽 하나
- 훌륭한 객체지향 설계 = 협력하는 객체 사이의 의존성을 **적절하게 관리**하는 설계 (p.36). "무조건 낮추기"가 아니다.
- 못 짚은 축 두 개
  - **응집도** — 1장은 캡슐화의 효과를 결합도와 응집도 두 축으로 함께 말한다 (p.24~26). 정리에는 결합도 축만 있었다.
  - **의인화** — "그래, 거짓말이다" 절. 현실에서 수동적인 대상도 코드 안에서는 능동적 존재로 만든다 (p.33 부근).

## 프론트엔드 착지

훅이 `items`를 통째로 내주는 순간 "정원은 10" 같은 규칙이 컴포넌트로 새어나간다. `add(item)` 하나만 노출하면 컴포넌트는 여전히 `useCart`에 의존하지만(존재 의존은 남음), 내부 규칙에는 의존하지 않는다. 의존을 없애는 게 아니라 **얕게** 만드는 것.

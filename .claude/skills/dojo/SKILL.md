# /dojo {장} — 원리를 React 코드로 다시 만들기

목표는 자바 예제를 React 로 **번역**하는 게 아니다. 그 장에서 배운 **설계 원리**를
사용자가 직접 React/TS 코드로 다시 만들어 보며 손에 익히는 것. 책 예제와 비슷한
상황이면 좋지만 꼭 같을 필요는 없다.

시작하면 **모드를 사용자에게 고르게 한다.**

## 실행 (React 플레이그라운드)
dojo 파일은 브라우저에서 바로 렌더해 볼 수 있다.
- `npm run dev` → 개발 서버 실행(HMR). `playground/main.tsx` 상단에서 지금 실습
  중인 컴포넌트를 import 해 `Current` 에 연결하면 화면에 뜬다.
- `npm run typecheck` → 타입 검사만. before/after 리뷰 전에 돌려 타입 에러부터 정리.
- 실습 코드는 `dojo/{NN}/` 아래(예: `dojo/07/after.tsx`)에 둔다.

## 모드 A — 백지에서 만들기 (기본)
그 장의 원리가 **가장 선명하게 드러나는 React 상황을 3개** 제시한다. 조건:
- 실제 React 앱에 있을 법한 것. 원리 설명하려고 억지로 만든 예제 금지.
- **매번 다른 도메인**에서 뽑는다. 같은 소재가 반복되면 소재의 관성으로 풀게 되고
  원리가 안 남는다. (이전 dojo 도메인을 피한다 — `dojo/` 하위 폴더 확인)
- 상태가 있고 관심사가 둘 이상 얽힌 상황. 너무 단순하면 설계 판단이 안 생긴다.
- 각 후보는 **두 줄 이내**. **어느 원리가 어디서 걸리는지는 말하지 않는다.**

사용자가 하나 고르면 `dojo/{NN}/` 에 **사용자가 직접** 코드를 쓴다.
**이때 너는 손대지 않는다.** 다 썼다고 하면 리뷰로 넘어간다.

## 모드 B — 고치기
그 장의 원리를 **정확히 위반하는** React 코드를 **60~120줄**로 만들어
`dojo/{NN}/before.tsx` 에 저장한다. **어디가 문제인지는 말하지 않는다** — 사용자가
찾는다. 사용자가 `dojo/{NN}/after.tsx` 로 고치면 리뷰한다.

## 리뷰 (두 기준)
after 코드(또는 A 모드 결과물)를 두 기준으로 본다. 각 지적은 **한 줄 + 근거**.

1. **책의 기준** — 응집도 / 결합도 / 의존성 방향 / 캡슐화 / 책임 할당.
   각 항목 한 줄 + **페이지(p.xx)**. 원문 근거는 book-reader 에 위임해 얻는다.
2. **Toss Frontend Fundamentals** — 가독성 / 예측 가능성 / 응집도 / 결합도.
   FF 기준을 적용할 때는 **`refs/toss-ff/` 에서 실제 근거를 찾아 단다**
   (book-reader 에 출처 `toss-ff` 로 위임, 청크 경로/제목 인용).

### 두 기준이 엇갈리는 지점을 반드시 짚는다
책 기준으론 옳은 추상화가 FF 가독성 기준으론 과한 간접 참조가 되는 경우 같은 것.
**이게 제일 좋은 글감이다.** 발견하면 명확히 표시한다.

리뷰도 원칙 1을 따른다. 문제를 다 짚어주기 전에, 먼저 "여기서 뭐가 걸려?" 로
사용자가 스스로 찾게 유도하고, 못 찾으면 힌트→공개 순으로.

## translation.md 갱신
원리별로 한 줄씩 누적한다. `그대로 성립 / 형태를 바꿔야 성립 / 성립하지 않음` +
이유(React 맥락) + 근거. 자바 문법에 묶인 원리를 React 에 억지로 가져오지 않도록
이 판정을 남긴다.

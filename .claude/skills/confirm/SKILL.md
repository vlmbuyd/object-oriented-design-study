# /confirm {장} — 내 언어로 한 정리를 엄밀하게 검증하기

`/ask` 는 **모른다는 걸 알 때** 쓴다. 이건 **안다고 믿을 때** 쓴다.
검증 대상은 질문이 아니라 이미 완성된 **진술**이다.

사용자는 이미 한 번 답을 낸 상태다. 그래서 원칙 1의 3단 계단이 이렇게 접힌다:

| 원칙 1 | 이 스킬에서 |
|---|---|
| 1단계 힌트 | **2. 판정** — 어디가 걸리는지만. 왜 틀렸는지는 아직 |
| 2단계 재시도 채점 | **3. 방향 → 4. 재판정** |
| 3단계 공개 | **5. 풀어서 설명** |

**"제대로 이해시켜주는 것"은 5단계에서만 일어난다.** 2~3단계에서 설명을 시작하면
이 스킬은 그냥 첨삭기가 된다.

---

## 1. 입력 받기

- 붙여넣기, 또는 파일 경로(`notes/`, `scratch/`, `writing/`).
- **`writing/` 은 읽기만 한다. 절대 수정하지 않는다** (사용자 소유).
- 아무것도 없으면 먼저 요청한다: **"이 장을 네 말로 한 문단 써봐. 책 단어 안 봐도 돼."**
  요약을 대신 써주고 검토하는 건 이 스킬이 아니다.

## 2. 명제로 쪼개고 판정만 한다

사용자 글을 **명제 5~12개**로 자른다. **인용은 사용자 문장 그대로.** 다듬지 않는다.

| 기호 | 뜻 |
|---|---|
| ✅ | 맞음 |
| ⚠️ | 반쯤 — 결론은 맞는데 용어·근거가 미끄러짐 |
| ❌ | 틀림 |
| ➕ | 책이 그렇게 말한 적 없음 (과잉일반화·자기 창작) |
| 🕳 | 빠진 축 — 이 장의 핵심인데 명제가 아예 없음. **최대 2개** |

⚠️/❌/➕ 에는 **정답 대신 좌표만** 준다. "여기서 X 와 Y 를 같은 걸로 쓰고 있어"
까지가 한계. "왜냐하면…" 이 나오려 하면 멈춘다.

원문 근거는 **book-reader 서브에이전트에 위임**해 `(p.xx)` 만 받아 단다.
청크를 직접 열지 않고, 받은 문단을 대화에 붙여넣지 않는다.

## 엄밀함의 기준 — 자기 언어 정리가 무너지는 다섯 지점

명제를 훑을 때 이 다섯 축을 **명시적으로** 통과시킨다. 이게 이 스킬의 핵심이다.

1. **용어 치환 미끄러짐** — 책 용어를 일상어로 바꾸면서 뜻이 넓어지거나 좁아짐.
   ("캡슐화" → "숨기기" 로 바꾸면 무엇이 빠지는가)
2. **인과 뒤집힘** — 결과를 원인 자리에 놓음.
   (응집도가 높아서 변경이 쉬운 건가, 변경이 쉬운 걸 응집도가 높다고 부르는 건가)
3. **범위 과장·축소** — "항상", "모든", "무조건" 이 붙었는가. 조건절이 사라졌는가.
4. **층위 혼동** — 책이 굳이 구분한 것을 뭉갬. 메시지/메서드, 역할/책임/객체,
   클래스/타입, 구현/인터페이스.
5. **예시로만 이해** — 예시는 맞는데 원리 문장이 없음. React 사례로만 설명했다면
   여기 걸릴 확률이 높다. 예시를 걷어내고도 문장이 서는지 본다.

걸린 축만 말한다. **하나도 안 걸리면 "다 통과" 라고 말한다.** 억지로 만들지 않는다.

## 3. 개선 방향만 준다

- **최대 3개.** 각 한 줄. 명제 번호를 붙인다.
- 고쳐 쓴 문장을 주지 않는다. 사용자가 쓸 자리다.
- 예: "명제 4 — '역할' 자리에 네가 쓴 단어를 '객체'로 바꿔 읽어봐. 문장이 그대로
  성립하면 둘을 같은 걸로 쓰고 있는 거야."
- 그리고 요청한다: **"이 방향으로 다시 써봐. 걸린 명제만."**

사용자가 "그냥 답 알려줘" 해도 3단계는 준다. 그래도 다시 요구하면 5로 넘어간다.

## 4. 재판정

다시 쓴 문장을 **맞았는지/틀렸는지만** 말한다. 남은 것에만 **더 좁은** 방향 하나.
여기까지도 설명은 없다.

## 5. 이제 푼다 — 이 스킬의 존재 이유

두 번째 시도까지 끝났으면 **연다.** 순서를 지킨다.

1. **네 정리가 서 있던 자리** — 어떤 그림을 그리고 있었는지 한 줄로 되비춘다.
   (틀렸다고 시작하지 않는다. 어디서 갈라졌는지가 요점이다)
2. **책이 서 있는 자리** — 짧게. `(p.xx)`.
3. **반례 하나 — 필수.** 사용자의 원래 문장이 **구체적으로 깨지는 상황**을 만든다.
   추상적 재설명 열 줄보다 반례 하나가 이해시킨다.
4. **React/TS 로 착지** — 이 저장소의 목표다. 이 원리가 프론트에서 어떤 모양으로
   나타나는지 한 예. 성립하지 않는다면 그렇다고 말한다.

**전체 15줄 이내.** 장 요약을 새로 쓰지 않는다.

닫는 말은 항상 되묻기다: **"이제 네 말로 한 문장이면?"**
사용자 문장이 나와야 이 세션이 닫힌다.

## 기록: `scratch/{NN}.md` 에 append

`## 검토 (/confirm)` 아래에 붙인다. 덮어쓰기 금지. `/wrap` 이 여기서 집어간다.
**`notes/` 에 직접 쓰지 않는다** — 저장 분배는 `/wrap` 책임이다.

```
[원문] (사용자 1차 정리. 한 글자도 고치지 않는다)
[판정] 3 ⚠️ 역할과 객체를 같은 것으로 씀 (p.87)
[판정] 5 ❌ 인과가 뒤집힘
[고쳐 씀] (사용자 2차 문장 그대로)
### 카드 후보 — [ ] "..."
```

- `[고쳐 씀]` 은 **사용자 문장으로만** 채운다. 5단계의 내 설명을 요약해 넣지 않는다.
- ❌ 와 ➕ 판정을 받은 명제는 **전부** `### 카드 후보` 로 내린다.
  여기서 `review.py add` 를 직접 부르지 않는다. 등록은 `/wrap` 담당.

## 기록

```
python3 scripts/log_event.py --type confirm --chapter {NN} --score <✅ 수 / 전체 명제 수> --tags <걸린 개념들>
```

`--score` 는 **1차 판정 기준**이다(고친 뒤 점수가 아니다). `/drill` 과 같은 축으로
집계돼서 `/retro` 가 약점 추이를 본다.

## 하지 말 것

- **2~4단계에서 정답 흘리기. 가장 흔한 실패다.**
- 사용자 문장을 고쳐서 인용하기. 틀린 문장도 그대로 인용한다.
- **엄밀함을 트집으로 바꾸기.** 맞는 걸 억지로 흠집 내지 않는다. 다 맞으면 "다 맞다"
  하고 대신 경계를 시험하는 질문 하나를 준다: "그럼 이게 깨지는 경우는?"
- 걸린 곳을 다 나열하기. 방향은 3개, 🕳 는 2개까지.
- `writing/` 의 파일 수정.
- 사용자가 안 쓴 부분까지 이 장 전체를 요약해 채워주기.
